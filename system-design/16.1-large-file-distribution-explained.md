# Part 1: Glossary (read this first)

## 1.1 Units and speed

**Byte vs bit.** A byte is 8 bits. Disks and file sizes are measured in **bytes** (GB = gigabytes). Network speeds are measured in **bits** per second (Gbps = gigabits per second). This is the number-one source of arithmetic mistakes.
- Conversion: **divide Gbps by 8 to get GB/s.** A 10 Gbps network card moves 10 ÷ 8 = **1.25 GB/s**.

**GB, TB.** 1 GB = 1,000 MB. 1 TB = 1,000 GB. (We use decimal units to keep the arithmetic clean; real systems sometimes use 1,024.)

**Throughput / bandwidth.** How much data per second a link or device can move. Think of it as the **width of a pipe**. Unit: GB/s or Gbps.

**Latency.** How long one thing takes (milliseconds). Not the main concern here, because we are moving huge files, so throughput dominates.

**Sequential write speed.** How fast a disk can write a big file in one continuous stream (as opposed to many tiny scattered writes). A SATA SSD does about **500 MB/s**. NVMe (a faster SSD type) does several GB/s.

## 1.2 Datacenter hardware and network

**Machine / host / node / server.** One computer. We use these interchangeably.

**NIC (Network Interface Card).** The network port inside a machine. Its speed caps how fast that one machine can send or receive. Ours: **10 Gbps = 1.25 GB/s**.

**Rack.** A tall metal cabinet that holds roughly 20 to 40 servers stacked vertically. Machines in the same rack are physically next to each other and share the same network switch. We assume **40 machines per rack**, so 10,000 machines = **250 racks**.

**ToR switch (Top-of-Rack switch).** A network switch mounted at the top of each rack. Every machine in the rack plugs into it. Traffic between two machines in the *same* rack goes machine → ToR → machine and never leaves the rack. **ToR is also the single device that connects the whole rack to the rest of the datacenter**, which is why a ToR failure takes out all 40 machines at once.

**Uplink.** The connection from the ToR switch **up** to the next network layer (the spine). It is the rack's single doorway to the outside world. Ours: **40 Gbps = 5 GB/s**, shared by all 40 machines in the rack.

**Spine.** The network layer above all the racks that connects every ToR to every other. We assume it is "non-blocking", meaning it has enough capacity that it is never the bottleneck, so we can ignore it.

**Oversubscription.** When the doorway is narrower than the sum of everything that wants to use it.
- Inside the rack: 40 machines × 10 Gbps = **400 Gbps** could be sent or received at once.
- Out of the rack: the uplink is only **40 Gbps**.
- Ratio 400 : 40 = **10:1 oversubscribed**.
- This is normal and deliberate (it saves money, because machines rarely all talk to other racks at once). But for *this* workload, where every machine wants 10 GB from outside at the same time, the narrow doorway matters a lot.
- Analogy: a building with 40 apartments and one elevator. Fine normally; terrible during a fire drill.

**East-west / cross-rack traffic.** Traffic that travels between racks (through the uplinks and spine). This is the **expensive, scarce** kind of traffic here. Traffic that stays inside a rack is **rack-local** and is cheap and plentiful.

**Ingress / egress.** Ingress = data coming **in** to a machine or service. **Egress = data going out.** "Origin egress" means "how much data the origin server can send out per second". Cloud providers also charge money for egress, so it is both a speed limit and a cost.

**Rack-aware.** The software knows which rack each machine is in and uses that fact to make decisions. In this design: "prefer to fetch data from a neighbour in my own rack." The opposite is topology-blind, meaning it picks any peer at random.

**Topology.** The physical layout and wiring (which machine is in which rack, which racks are in which datacenter). "Topology-aware" is the general term; "rack-aware" is the most common form.

## 1.3 The design vocabulary

**Origin.** The server where the file originally lives. The first source of the data.

**Seed.** Any machine that has the **complete** file and is willing to serve it to others. The origin is the first seed. Over time, machines that finish downloading become seeds too.

**Peer.** Another machine in the group that is also downloading or sharing the file.

**P2P (peer-to-peer) / swarm.** Instead of everyone downloading from one server, **machines download from each other**. The group of machines trading pieces is called a **swarm**. This is how BitTorrent works. The key property: **every downloader is also an uploader**, so capacity grows as the number of machines grows.

**Chunk.** We cut the 10 GB file into fixed-size pieces (here **16 MB each, giving 625 chunks**). Peers trade chunks, not the whole file. This lets a machine start sharing chunk #5 while it is still downloading chunk #400.

**Hash (SHA-256).** A fingerprint of data: a fixed-size number (32 bytes) computed from the contents. If even one bit of the data changes, the fingerprint changes completely. We use it to check that a chunk arrived intact.

**Manifest.** The "table of contents" for the release: file size, chunk size, and the **expected hash of every chunk** (625 hashes × 32 bytes ≈ 20 KB), plus a root hash for the entire file. It is tiny compared to the file.

**Signed manifest.** The manifest carries a **digital signature** from the publisher. Machines check the signature, so they know the table of contents (and therefore every chunk hash) came from someone authorised, not from an attacker.

**Tracker (coordinator).** A small service that does **not** carry file data. It only (a) hands out the manifest, (b) tells each machine "here are some peers you can ask", and (c) collects progress reports. Think of it as a phone book plus a progress dashboard. "Not on the data path" means that if it dies, data that is already flowing keeps flowing.

**Agent.** A small program running on every machine that does the downloading, verifying, sharing and progress reporting.

**Announce.** The agent's periodic check-in with the tracker: "I'm machine X in rack Y, here are the chunks I have; who else should I talk to?"

**Bitmap ("have map").** A string of 625 bits, one per chunk: 1 means "I have it", 0 means "I don't". Tiny (about 79 bytes) and very cheap to send around.

**Rarest-first.** The chunk-picking rule: always download the chunk that **the fewest peers currently have**. That spreads rare chunks quickly, so no chunk depends on a single holder. If you instead download in order, everyone would want chunk 1 at the same time and the swarm would have nothing new to share.

**Endgame mode.** For the last few chunks, ask **several peers for the same chunk at once** and cancel the extra requests when the first one arrives. This stops one slow peer from holding up the final 1%.

**Web seed.** A normal web or blob-store URL that serves the same file over plain HTTP. It acts as a backup source of chunks if the swarm is missing something.

**Blob store.** Large-object storage service (Google Cloud Storage, Amazon S3). You upload a file, and many clients can download it over HTTP.

**Staged vs active.** *Staged* means the file is fully downloaded, verified, and sitting on disk, but **nothing is using it yet**. *Active* means the service has switched over to using the new file. We keep these as two separate steps on purpose.

## 1.4 Reliability and operations vocabulary

**Bottleneck.** The one part of the system that limits overall speed. Fix it and the next-slowest part becomes the new bottleneck.

**Floor (lower bound).** The fastest time physically possible, ignoring everything else. Here: a machine cannot finish faster than 10 GB ÷ its disk speed.

**SPOF (single point of failure).** A single component whose failure stops everything.

**SLO / SLI.** SLI = a measurement (e.g. "% of machines finished"). SLO = the target for it (e.g. "99% within 5 minutes").

**p50 / p99.** The 50th and 99th percentile. p50 = the typical machine's time. **p99 = the time within which 99% of machines finished** (so 1% were slower). The slowest few machines are called the **tail** or **stragglers**; they often define "done".

**Thundering herd.** Thousands of machines all doing the same thing at the same instant (e.g. all contacting the tracker at second zero) and overwhelming something. Fix: **jitter**, which means adding a random delay so they spread out.

**Canary / waves.** Rolling a change to a small slice first (1%), checking health, then widening (10%, then 100%). A bad release hurts few machines instead of all.

**Admission control.** The server deliberately accepts only a limited number of simultaneous requests and makes the rest wait, to protect itself.

**mTLS (mutual TLS).** Encrypted connection where **both sides** prove their identity with certificates. Used so only legitimate agents can talk to each other.

**Idempotent.** Doing it twice has the same effect as doing it once (e.g. re-downloading chunk 7 just overwrites chunk 7 with identical bytes). It makes retries safe.

**NALSD (Non-Abstract Large System Design).** Google's interview and design style: not just boxes and arrows, but **real numbers with units**. You compute how many machines, how much bandwidth and how much time, find what breaks first, fix it, and recompute.

# Part 2: The Interview Narrative

*Read each section as what you would say. Notes in italics explain why.*

## Step 1: Clarify before designing (about 30 seconds)

> "Before I design anything, I'd like to pin down four things, because each one changes the answer.
> First, is the file **immutable**, meaning it never changes once published, and how often do new versions come out? That tells me whether it's worth sending only the parts that changed next time.
> Second, what's the **time target**? Seconds, minutes, or hours? If the answer is 'a few hours', I'd choose something much simpler than if it's 'a couple of minutes'.
> Third, is this **one datacenter or several**, and what does the network look like: how many machines per rack and how fat the links out of a rack are?
> Fourth, are these machines **idle or serving live traffic**? If they're serving users, I can't let a file transfer eat their bandwidth or disk."

*Why this matters: these questions are not stalling. Each one maps to a design decision later (delta transfer, choice of approach, rack-awareness, bandwidth caps).*

## Step 2: State assumptions out loud

> "I'll assume the following, and I'll flag where the answer would change if you disagree.
> The file is **10 GB**. There are **10,000 machines**, **40 per rack**, so **250 racks**.
> Each machine has a **10 Gbps network card**. Network speeds are in bits, so that's 10 divided by 8, which is **1.25 gigabytes per second**.
> Each machine's disk writes sequentially at about **500 megabytes per second**, typical for a SATA SSD.
> Each rack connects to the rest of the datacenter through a **40 Gbps uplink**, which is **5 GB per second**. Inside the rack, 40 machines could together push 400 Gbps, so the uplink is **10 to 1 oversubscribed**. That ratio is going to matter.
> The origin, the server holding the file, has a 10 Gbps link, so **1.25 GB per second of egress**, meaning data going out."

*Why the 10:1 ratio gets flagged now: it is the setup for the insight in Step 6. Mentioning it early shows you know where the design will be pinched.*

## Step 3: The naive approach and why it fails (the first bottleneck)

> "Let me start with the simplest thing: every machine downloads from the origin.
> Total data to move is 10 GB times 10,000 machines, which is **100,000 GB, or 100 terabytes**.
> The origin can send **1.25 GB per second**. So 100,000 divided by 1.25 is **80,000 seconds, about 22 hours**.
> If the goal is a few minutes, that's off by roughly **270 times**. The **bottleneck is the origin's outgoing bandwidth**. Everything funnels through one pipe.
> I could add more origin servers, but to get down to even 80 seconds I'd need roughly a thousand of them. That doesn't scale, so the real fix is to **stop having the origin be the one that serves everyone**."

*Check the arithmetic yourself: 22.2 hours ÷ 80 seconds ≈ 1,000. Think of it as one water tap filling 10,000 buckets. Adding a few more taps doesn't help much; you need the buckets to pass water to each other.*

## Step 4: The physical floor: what's the best anyone could do?

> "Before improving further, I want to know the **floor**: the best any design could possibly achieve.
> Each machine has to receive and write 10 GB. The network card can take 10 GB in 10 divided by 1.25 equals **8 seconds**. The disk writes at 0.5 GB per second, so 10 divided by 0.5 equals **20 seconds**.
> The disk is slower than the network, so **no design can finish a machine in under about 20 seconds**. That's the physics. Everything else I add is overhead on top of that 20."

*Why this is a strong move: it gives you a target and a stopping point. You know the design is "done" when you reach 20 s (plus realistic overhead), instead of optimising forever.*

## Step 5: Idea: let the machines share with each other

> "The insight is that these 10,000 machines each have a network card and a disk sitting there. If every machine that gets a piece of the file can pass it on to others, then **total sending capacity grows with the number of machines**, instead of being stuck at one origin. This is the **peer-to-peer** or **swarm** model, the same idea as BitTorrent.
> To make that work, I'll **cut the file into chunks**, 16 MB each. 10 GB divided by 16 MB gives **625 chunks**. A machine can start passing along chunk 5 while still downloading chunk 400, so the data flows like a pipeline instead of waiting for whole-file completion.
> To make sure nothing gets corrupted, the publisher computes a **SHA-256 fingerprint of every chunk** and puts them in a **manifest**: 625 hashes of 32 bytes each is about **20 KB**, tiny. The publisher **signs** the manifest. Every machine checks each chunk it receives against the manifest, so a corrupted or malicious chunk is rejected and re-fetched. The manifest signature means an attacker can't swap in their own fingerprints."

## Step 6: The key insight: it's not enough to be peer-to-peer, it has to be rack-aware

> "Here's where the network layout matters. If each machine picks peers **at random**, then almost all of its peers are in *other* racks: 249 of the 250 racks, so about 99.6%.
> Let me compute what that does to one rack. 40 machines each need 10 GB, nearly all of it arriving from other racks. That's about **400 GB that has to come in through the rack's uplink**. The uplink carries 5 GB per second, so 400 divided by 5 is **80 seconds**. That's **four times worse than the 20-second disk floor**. The uplink, the narrow doorway, has become the bottleneck.
> The fix is to make the software **rack-aware**: it knows which rack each machine is in and prefers to fetch chunks from a neighbour in the same rack. Neighbours talk to each other through the top-of-rack switch and never touch the uplink.
> With that, the whole rack only needs **one copy of the file from outside**: 10 GB through the uplink instead of 400 GB. Then the 40 machines **share chunks among themselves** inside the rack. 10 GB divided by 5 GB/s is **2 seconds** of uplink time, which is no longer a concern.
> Across the whole fleet, cross-rack traffic goes from 100 TB to 250 racks times 10 GB, which is **2.5 TB, a 40-times reduction**."

*Why 40: it's the number of machines per rack. Each rack pulls one copy instead of 40 copies, so traffic drops by exactly the rack size. If racks were 20 machines, the saving would be 20×.*

*How does one copy get shared if every machine needs different chunks first? Each machine in the rack pulls a different slice of the chunks from outside (together, one full copy), then they swap slices with each other inside the rack. That's the rack-local sharing the scheduler favours.*

## Step 7: What does the origin actually have to do now?

> "The origin only needs to push each chunk into the swarm about **once**, not once per machine. One full copy out of the origin is 10 GB divided by 1.25 GB/s, **8 seconds**. I'd budget about 3 times that for redundancy and faster spreading, so roughly **24 seconds of origin egress**, about **30 GB total instead of 100 TB**. That's around 3,000 times less load on the origin, and it overlaps with the swarm spreading, so it adds no extra waiting."

*This is the payoff of the swarm: the origin's workload becomes almost independent of how many machines there are.*

## Step 8: Components and what each one does

> "The system has four parts.
> **Publisher**, which is the build or CI system. It splits the file into chunks, hashes them, signs the manifest, and uploads the file to the origin.
> **Origin seeds**: 2 to 3 replicas, plus a blob store such as GCS as a backup 'web seed'. Replicas mean no chunk exists on just one machine.
> **Tracker**, a small replicated service. It hands out the manifest, gives each agent a list of peers sorted **same rack first, then same row, then anywhere**, and collects progress. Importantly, **it's not on the data path**: if it dies mid-rollout, agents keep trading with the peer lists they already have.
> **Agent**, a small program on each machine. It fetches the manifest, announces which chunks it has, downloads and verifies chunks, writes them to a pre-allocated file, serves chunks to peers, and finally verifies the whole file before marking it **staged**."

## Step 9: API

> "Three interfaces.
> **Publisher to tracker**, over gRPC: `CreateRelease` with the file location, root hash, target machines and rollout policy. `Activate` which I'll come back to. `AbortRelease`. And `GetStatus`, which returns counts by state, p50 and p99 completion times, per-rack coverage, and bytes served by origin versus by peers.
> **Agent to tracker**: `GetManifest`, `Announce` (which sends my rack ID and my chunk bitmap and returns a list of peers plus when to check in next), and `ReportProgress` with a state like PENDING, DOWNLOADING, VERIFYING, STAGED or FAILED.
> **Peer to peer**: a plain HTTP/2 `GET /chunk/{release_id}/{index}`, over mutual TLS, so only legitimate agents can fetch or serve chunks."

*Why gRPC vs HTTP: gRPC for small structured control calls; plain HTTP for bulk bytes (simple, supports byte ranges, easy to proxy and debug). Don't over-explain; the interviewer cares about the shape, not the protocol.*

## Step 10: How the agent behaves (scheduling rules)

> "A few rules in the agent make the numbers actually come true.
> **Rarest-first**: always fetch the chunk the fewest peers have. That spreads every chunk quickly, and if the origin vanishes, no chunk is stuck on one machine.
> **Rack-local preference**: only go cross-rack when no neighbour has the chunk.
> **Per-host caps** on download rate, upload rate and disk I/O. These machines might be serving real traffic and I don't want a file transfer to hurt them. This is the same idea as a rate limiter, pointed at my own fleet.
> **Parallelism**: keep 4 to 8 chunk requests in flight so one slow peer can't stall everything.
> **Endgame mode**: for the last few chunks, ask several peers for the same chunk and cancel duplicates once one answers. That chops the tail.
> **Startup jitter**: spread the first check-in randomly over 10 to 30 seconds, so 10,000 agents don't hit the tracker and origin at the same instant (a thundering herd). The origin accepts only a handful of initial connections; everyone else bootstraps through the swarm.
> **Preflight**: check there's enough free disk space before starting, and fail fast with a clear reason if not.
> **Resume**: save the chunk bitmap next to the partial file so a crash resumes from where it left off."

## Step 11: Control plane check (don't assume it's fine)

> "I should check that the coordination layer isn't itself a bottleneck. If each agent announces every 10 seconds, that's 10,000 divided by 10 equals **1,000 announces per second**. Each response is around 2 KB, so about **2 MB per second** total. Connections: each host talks to about 40 peers, so around **400,000 connections**, 40 per host. That's trivial for a replicated tracker, so no sharding needed. The data plane is the hard part; the control plane isn't."

## Step 12: Be honest about the real-world speed (host caps)

> "20 seconds is the lower bound, but I wouldn't let the transfer run at full speed on a machine serving traffic. If I cap each host's download rate, the time becomes: uncapped 20 seconds; 2 Gbps cap, 40 seconds; 1 Gbps, 80 seconds; 500 Mbps, 160 seconds. Even at 500 Mbps, we'd meet a 5-minute target. The cap is a **product decision, not a protocol limit**, so I'd ask what's acceptable and maybe raise it off-peak.
> Putting it together, I'd quote a realistic target of **median around 1 minute and 99th percentile around 3 minutes**, once you add caps, hashing overhead, startup and the tail."

*Hashing cost, for completeness: SHA-256 runs at roughly 1 GB/s per CPU core, so verifying data arriving at 0.5 GB/s uses about half a core. Small, but it counts toward "don't hurt production".*

## Step 13: Compare alternatives, and say when you would NOT build this

> "I considered four approaches.
> **A, single origin**: 22 hours. Fails.
> **B, pull from a blob store** like GCS: if the store can sustain about 100 GB/s in total, 100 TB divided by 100 GB/s is 1,000 seconds, roughly **17 minutes**. Simplest to run, no agents. But it's bounded by per-object limits and costs egress money, and it doesn't know about racks.
> **C, a tree**: origin feeds regional servers, which feed rack leaders, which feed hosts. About 14 levels for 10,000 machines at roughly 20 seconds each, so around **5 minutes**. Predictable, but if a node in the middle dies, everything under it is orphaned.
> **D, rack-aware swarm**: about **1 to 3 minutes**. Time stays roughly flat as the fleet grows, and it heals itself. The cost is more moving parts: an agent and a tracker.
> My rule: **if the target is 20 minutes or more, I'd pick B for its simplicity.** If the target is a few minutes, or the file or fleet will grow, I'd pick D, because B's time grows with fleet size and D's doesn't. And I'd keep B around as the **fallback seed** inside D."

*Saying "I wouldn't build the complex thing if the simple one meets the requirement" is a seniority signal. Say it deliberately.*

## Step 14: The bottleneck ladder, summarised

> "To recap how the bottleneck moved as I fixed things: the **origin's outgoing bandwidth** first, at 22 hours. Adding origin replicas doesn't scale, so I let receivers serve each other. Then it was the **rack uplink**, at 80 seconds, which I fixed with rack-awareness. Then the **per-machine disk**, at 20 seconds, which I accept as the floor. Then the **host-impact cap**, which is a choice. Finally the **stragglers** in the tail, which I handle with endgame mode, timeouts and retries.
> Notice the pattern: the bottleneck moved from the origin, to the network core, to the **individual machine**. The design is finished when the next bottleneck is something I can't, or shouldn't, remove."

## Step 15: Failure modes

> "Let me walk through what can go wrong.
> **Origin dies mid-rollout.** I keep 2 to 3 origin replicas plus the blob-store web seed, and I don't announce widely until each chunk exists on at least two holders.
> **Tracker goes down.** Agents keep using cached peer lists and can swap peer addresses with each other. The tracker is replicated, and agents fall back to a rate-limited web seed.
> **Corrupt chunk, bad disk, or malicious peer.** Every chunk is checked against the signed manifest. A bad chunk is dropped and re-fetched from someone else, repeat offenders are banned, and the whole-file hash is verified before I mark the machine staged.
> **Tampered release.** The manifest is signed, agents authenticate each other with mTLS, and publishing is access-controlled.
> **Slow or hung peer.** Per-request timeouts, many parallel peers, endgame duplicates.
> **Machine crashes mid-download.** The saved bitmap lets it resume; downloads are idempotent.
> **Disk full.** Caught by the preflight check; the agent reports FAILED with a reason and never partially activates.
> **A whole rack's switch fails.** That's 40 machines gone and rack-local sharing for that rack lost. The swarm routes around it, and the rack retries when it comes back.
> **Cold-start herd.** Jittered start and admission control on the origin and tracker.
> **Hurting production.** Bandwidth and disk caps, and an abort hook that stops the rollout if serving latency regresses.
> **Mixed versions across the fleet.** That's why activation is a separate step, which I'll explain next.
> **Multiple datacenters.** The WAN between datacenters becomes the new narrow doorway, so I pull **one copy per datacenter** across it, then swarm locally."

## Step 16: Operations: distribute first, activate later

> "One design principle I care about: **distribution and activation are two separate steps.** When a machine finishes downloading and verifying, it's **staged**: the file is on disk but nothing uses it. Then a separate `Activate` call flips machines to the new file in **waves**, 1%, then 10%, then 100%, with health checks between waves. That way a bad release hurts 1% of machines, not everything, and I can roll back instantly because the previous version is still on disk.
> For monitoring: percent of machines staged, time to p50 and p99, bytes from origin versus bytes from peers, the share of traffic that stayed within a rack, hash failure rate, throttling events, and tracker latency.
> Alerts: any machine with no progress for 60 seconds; origin egress far above expected, which means the swarm isn't working; and any rack stuck at 0%.
> Two numbers I'd check first in production: origin egress should be tens of GB, not 100 TB; and the rack-local byte share should be around 95% or higher."

## Step 17: Likely follow-up questions

> **"What about next week's new version?"** "If most of the file is unchanged, I'd split by content so identical chunks are recognised. If 90% is unchanged, I'd move about 1 GB instead of 10. Worth it only if versions are frequent and similar."
>
> **"Why not multicast?"** "Multicast sends one stream to many receivers and looks ideal on paper, but it needs special network support, has no per-chunk retransmission or integrity story, and is fragile to operate in most datacenter networks."
>
> **"How is this different from a CDN?"** "A CDN caches content near users and pulls on demand. Here I know the full set of receivers in advance and they all want the file at once, so coordinated, rack-aware sharing beats per-request caching."

# Part 3: The 60-Second Version (memorise this)

> "100 TB total. One origin at 1.25 GB/s takes 22 hours, so the origin can't serve everyone. I cut the file into 625 chunks of 16 MB, publish a signed manifest of chunk hashes, and let machines share chunks with each other, a swarm. But random peering still crams about 400 GB through each rack's 5 GB/s uplink, 80 seconds, so I make it rack-aware: one copy per rack from outside and the rest shared inside the rack, which cuts cross-rack traffic 40 times. The true floor is each machine's disk, 20 seconds, so I target about 1 minute median and 3 minutes p99 after bandwidth caps. Every chunk is verified, the tracker is off the data path, and files are staged first and activated in waves. If the deadline were 20 minutes or more, I'd just pull from a blob store."

# Quick Self-Test (answer without looking)

1. Why do we divide a network speed in Gbps by 8?
2. What is a ToR switch, and what does its failure cost you?
3. Why is 10 Gbps on 40 machines through a 40 Gbps uplink a problem for this workload?
4. Why does random P2P take 80 s but rack-aware take 2 s for the uplink?
5. Why is the floor 20 s and not 8 s?
6. What does "staged, then activated" protect you from?
7. At what deadline would you skip all this and use a blob store?

**Answers:** (1) bits to bytes; (2) the switch connecting 40 machines to the datacenter, so you lose the whole rack; (3) 10:1 oversubscription, so cross-rack bulk transfer is squeezed; (4) 400 GB vs 10 GB must cross the uplink, at 5 GB/s; (5) disk is slower than the network card; (6) a bad or half-distributed release affecting the whole fleet at once; (7) around 20 minutes or more.
